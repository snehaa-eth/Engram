sha# Fact stores and prompt caches win the race

The research points to a clear answer. The fastest, most token-frugal "AI brain" is not a bigger graph or a cleverer compressor. It is a **cascade**. Stable context (tools, persona, a small user or tenant profile) sits in a provider-cached prefix that bills at **0.025–0.1x** the normal input price. Behind it is a small store of atomic facts, consolidated when they are written, with validity dates attached. A cheap router chooses between no retrieval, a single hybrid lookup over that store, graph-based multi-hop retrieval, or agentic search over raw history, and it escalates only when the cheaper path says "unanswerable." Every piece of that design has primary evidence behind it. Mem0's compact fact store cut retrieved context from **~26,000 to ~1,764 tokens per query**, with a **0.2 s p95 search** ([Mem0](https://arxiv.org/html/2504.19413)). Zep answered LongMemEval with **1.6k tokens instead of 115k** and scored *higher* than full context (71.2% vs 60.2% with gpt-4o) ([Zep](https://arxiv.org/html/2501.13956)). Gating retrieval removes **70–90% of retrieval calls** without losing accuracy ([TARG](https://arxiv.org/abs/2511.09803)). Two cautions matter as much as the wins. First, vendor-run memory benchmarks contradict each other by up to 26 points, so no current "state of the art" claim can be trusted without a neutral, same-harness re-run. Second, persistent memory turns a single prompt injection into a lasting compromise, so security has to be built into the write path from the start. The recommended service below targets roughly **20–60 ms of brain-side latency at p50** and **~600–1,200 uncached context tokens per query**. These are targets built from the cited components, not measured results. The benchmark plan at the end is designed to prove or disprove them against Mem0, Zep, Letta and HippoRAG.

## Provider caching saves more than compression, at zero quality risk

When an application runs on closed API models, the biggest token saving comes from not paying full price for tokens you send again, rather than from making the prompt shorter. Anthropic bills cache reads at **0.1x base input, 0.05x on Opus/Sonnet 5.5 and 0.025x on Fable/Mythos 5.1**. A 5-minute cache write costs 1.25x, a 1-hour write 2x, and the minimum cacheable prefix is 512 tokens ([Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). OpenAI now caches prefixes of 1,024+ tokens automatically, charges 0.1x for reads (0.05x on its newest models), and adds a write surcharge of 1.25x for its 30-minute TTL or 2.5x for its 12-hour TTL ([OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-caching)). The output is identical to an uncached call, so a cached prefix pays for itself after roughly one reuse within its TTL. The catch is that the prefix must match exactly. A change cascades in the order tools → system → messages. Editing a tool definition invalidates everything, and toggling thinking or effort settings invalidates the message cache ([Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). OpenAI warns explicitly that "summarization, compaction, or truncation can change the prefix and reduce reuse" ([OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-caching)). This one fact determines how a memory brain should be laid out. A profile block that gets rewritten every turn destroys the cache that makes it cheap.

Prompt compression is the second-tier tool, and its failure modes are well documented. Methods that output text work with black-box APIs: Selective Context, the LLMLingua family, RECOMP and Cmprsr. LLMLingua-2 is the practical drop-in. It is a ~0.55B encoder that classifies each token as keep or drop, runs **3–6x faster** than earlier compressors, and delivers **1.6–2.9x end-to-end latency gains at 2–5x compression** ([LLMLingua-2](https://arxiv.org/abs/2403.12968); [Cmprsr](https://arxiv.org/html/2511.12281)). RECOMP adds a cheap and important behavior: it can return an empty string when retrieved documents are irrelevant ([RECOMP](https://arxiv.org/abs/2310.04408)). The limits are severe on dense content, though. On GSM8K, LLMLingua-2 fell from 0.930 uncompressed to **0.513 at half length and 0.003 at one-tenth length**, while gpt-4.1-mini used as an abstractive compressor held **0.910** at half length ([Cmprsr](https://arxiv.org/html/2511.12281)). Compression can also *raise* total cost. When instructions are truncated, models generate longer outputs: a 5,400-call study measured roughly **56x output expansion on MBPP** under compression, against about 5x on HumanEval ([arXiv 2603.23527](https://arxiv.org/abs/2603.23527); single-author preprint). Soft-prompt methods reach dramatic ratios, but they need white-box access and still give up capability. 500xCompressor keeps only **62–73%** of uncompressed performance ([500xCompressor](https://arxiv.org/abs/2408.03094)), and xRAG compresses each document into one token by projecting its embedding into the model ([xRAG](https://arxiv.org/abs/2405.13792)). Neither can run against Claude or GPT.

These findings imply a division of labor. Caching covers the stable head of the prompt. Retrieval selection (retrieve less, and allow "nothing") covers the middle. Conservative 2–3x extractive compression applies only to bulky, non-repeated prose in the dynamic tail, such as retrieved documents or verbose tool logs, and never to instructions, code, numbers, IDs, names or dates. Compression and caching conflict wherever they touch the same tokens, so they must never be applied to the same segment.

## Memory systems cut tokens 7–70x, but on LoCoMo they do not beat full context

The memory literature has moved from differentiable memory inside the network to LLM-managed external stores. The 2025–2026 systems differ mainly in two choices: *when* they consolidate, and *how* they handle contradiction. Mem0 extracts candidate facts at write time from a rolling summary plus the last 10 messages. For each candidate it retrieves the 10 most similar existing memories, and an LLM chooses ADD, UPDATE, DELETE or NOOP. Mem0g stores entity triplets in Neo4j and **marks contradicted edges invalid instead of deleting them** ([Mem0](https://arxiv.org/html/2504.19413)). Zep/Graphiti keeps three tiers: a non-lossy episode subgraph, a semantic entity graph, and a community graph. It runs a **bi-temporal** model that separates when something was true from when it was ingested. On a contradiction it sets the old edge's t_invalid and deletes nothing. It retrieves with cosine plus BM25 plus breadth-first graph expansion, and reranks with RRF, MMR or a cross-encoder ([Zep](https://arxiv.org/html/2501.13956)). Letta's filesystem baseline is the opposite extreme. It does no write-time consolidation at all: raw history lives in files, and the agent calls `search_files` until it decides to answer ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). A-Mem lets new notes rewrite linked old notes ([A-Mem](https://arxiv.org/abs/2502.12110)). That adds adaptivity, but it also gives a single bad input a path to corrupt older memories.

The headline numbers have to be read in context. In Mem0's own LoCoMo evaluation with gpt-4o-mini, **full context scored 72.90 J and beat every memory system**: Mem0g 68.44, Mem0 66.88, Zep (as run by Mem0) 65.99, best plain RAG 60.97, OpenAI memory 52.90, A-Mem 48.38 ([Mem0](https://arxiv.org/html/2504.19413)). What the memory systems won was efficiency.

| System (Mem0 paper, LoCoMo) | J score | Search p95 | Total p95 | Context tokens/query | Store size/conversation |
|---|---|---|---|---|---|
| Full context | 72.90 | – | 17.12 s | ~26,031 | – |
| Mem0g | 68.44 | 0.657 s | 2.59 s | ~3,616 | ~14k |
| Mem0 | 66.88 | 0.200 s | 1.44 s | ~1,764 | ~7k |
| Zep (Mem0's run) | 65.99 | 0.778 s | 2.93 s | ~3,911 | >600k |

Source: [Mem0, arXiv 2504.19413](https://arxiv.org/html/2504.19413).

LoCoMo conversations average only about 16k–26k tokens, so they fit in context, and Zep argues the benchmark has no knowledge-update questions, a category with no ground truth, and mislabeled speakers ([Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). LongMemEval is harder and more credible. It has 500 questions over histories of ~115k tokens and tests extraction, multi-session reasoning, temporal reasoning, knowledge updates and abstention. Commercial assistants and long-context LLMs lose **~30% accuracy** over sustained interactions on it ([LongMemEval](https://arxiv.org/abs/2410.10813)). Here compressed memory wins on both axes. Zep scored **71.2% vs 60.2%** for full context with gpt-4o, at **2.58 s vs 28.9 s** and **1.6k vs 115k tokens** ([Zep](https://arxiv.org/html/2501.13956)). Chroma's Context Rot report reaches the same conclusion from the model side: across 18 models, focused ~300-token prompts consistently beat full ~113k-token prompts on LongMemEval, and distractors degrade performance ([Chroma](https://www.trychroma.com/research/context-rot)). Zep still *lost* on questions about what the assistant itself said earlier, dropping 94.6→80.4 with gpt-4o ([Zep](https://arxiv.org/html/2501.13956)). That is a direct warning: extraction pipelines that look only at user utterances silently drop assistant-side facts.

### The Mem0–Zep–Letta dispute shows that vendor numbers are not comparable

Depending on who ran the test, Zep's LoCoMo score ranges from **58.44 (Mem0's re-run) to 65.99 (Mem0's paper) to 75.14 (Zep's corrected figure) to 84 (Zep's original, retracted)**. Zep accused Mem0 of assigning both speakers the user role, putting timestamps into message text instead of `created_at`, and running Zep's two searches sequentially, which inflated latency ([Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). Mem0 replied that Zep's 84% had counted the adversarial category in the numerator and that Zep used a different prompt template and a single run. The GitHub thread closed for inactivity **with no agreed resolution** ([zep-papers#5](https://github.com/getzep/zep-papers/issues/5)). Letta then reported **74.0%** with nothing more than files and a search tool on gpt-4o-mini, and argued that "memory is more about how agents manage context than the exact retrieval mechanism used" ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). No neutral leaderboard exists that runs all of these systems under one harness. Any claim to "beat Mem0/Zep/Letta" therefore has to come with a published, reproducible harness, or it will join the dispute rather than settle it.

## Update-on-write fact stores beat similarity search when facts change

The most decision-relevant 2026 result comes from MERIT, a cost-metered benchmark of tool-using agents (23,440 episodes, $42.57 total). It found that embedding-retrieval memory was **unstable on updated facts (0.30–0.95 across models)**. Update-on-write stores, whether a structured fact store or LLM summarization, held at **0.70–1.00**. Adding hybrid retrieval on top of the fact store *lowered* performance. Agents acted on a correctly retrieved value **only 55% of the time**, the choice of memory implementation swung task success by up to **60 points**, and full-history replay was **never cost-effective** ([MERIT](https://arxiv.org/abs/2609.05441)). MERIT is a two-author preprint that has not been replicated. Still, it agrees with the mechanism: append-plus-similarity retrieval returns both the old and new value with nothing to say which is current. Preference retention fails in a similar way. On PrefEval, zero-shot preference-following accuracy drops **below 10% after only 10 turns (~3k tokens)** for most models. Reminders, self-critique and RAG help without solving the problem, and only fine-tuning improved it significantly ([PrefEval](https://arxiv.org/abs/2502.09597v1)).

Three design rules follow. Keep a small, pinned, explicitly maintained profile instead of hoping retrieval rediscovers preferences. Resolve contradictions at write time and *invalidate* old facts rather than deleting them, keeping event-time and ingest-time validity so the system can still answer "what did I believe in March?" ([Zep](https://arxiv.org/html/2501.13956)). And present retrieved facts to the model with their dates, status and source, because the retrieval-to-action gap is now as large as the recall gap. LongMemEval's own optimizations transfer directly: store at fact or round granularity, index chunks by their extracted facts, and expand queries using the time they mention ([LongMemEval](https://arxiv.org/abs/2410.10813)). The hybrid tension is real. Zep shows lexical + dense + graph fusion working well, while MERIT shows retrieval layered over a fact store hurting. The two can be reconciled by making the fact store authoritative and treating raw-episode retrieval as an escalation path, not a parallel source mixed into every prompt.

## Flat indexes and hybrid search are fast enough; graphs pay off only on multi-hop

Vector search is no longer the bottleneck at any scale an AI brain is likely to reach. HNSW gives roughly logarithmic search time ([HNSW](https://arxiv.org/abs/1603.09320)). DiskANN serves **one billion points from 64 GB RAM plus an SSD at under 3 ms mean latency and 95%+ recall@1** ([DiskANN](https://proceedings.neurips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html)). Quantization multiplies the headroom. Binary embeddings cut memory **32x** with a ~25x mean speedup and keep **~96.5%** of retrieval quality after rescoring; int8 cuts memory 4x and keeps **~99%** after rescoring. A 41M-document index shrinks from ~200 GB to ~5.2 GB ([Hugging Face](https://huggingface.co/blog/embedding-quantization)). Matryoshka embeddings support shortlisting on short vector prefixes and reranking on the full vectors, at up to **14x** faster retrieval ([MRL](https://arxiv.org/abs/2205.13147)). At the per-user or per-team scale of most tenants (10k–1M chunks), memory-bandwidth arithmetic puts exact brute-force search at about **0.3 ms for 10k, 3 ms for 100k and ~8 ms for 1M int8 vectors** on a laptop-class machine. That is an estimate from bandwidth, not a measurement ([retrieval notes, derived from HF and DiskANN figures](https://huggingface.co/blog/embedding-quantization)). Exact search means 100% recall at that scale, so approximate indexes earn their keep only for large enterprise tenants. Late interaction costs more: PLAID runs ColBERTv2 in tens of ms on GPU and tens to hundreds of ms on CPU ([PLAID](https://arxiv.org/abs/2205.09707)). Quality gains are more reliably available from cheap BM25 + dense fusion with reciprocal rank fusion, plus an optional small reranker.

Graph RAG is where indexing costs explode, and where the marketing numbers need context. HippoRAG 2's independent cost table, measured on an 11,656-passage MuSiQue corpus, is the most useful single comparison available ([HippoRAG 2](https://arxiv.org/html/2502.14802)):

| Method | Indexing input tokens | Indexing time | QA time/query |
|---|---|---|---|
| Dense (NV-Embed-v2) | 0 | 12.1 min | 0.3 s |
| RAPTOR | 1.7M | 100.5 min | 0.6 s |
| HippoRAG 2 | 9.2M | 99.5 min | 1.2 s |
| LightRAG | 68.5M | 235 min | 13.3 s |
| GraphRAG | 115.5M | 277 min | 10.7 s |

HippoRAG's "**10–30x cheaper and 6–13x faster**" claim is accurate but narrow. It compares online retrieval for 1,000 queries ($0.1 and 3 minutes) against *iterative IRCoT* ($1–3 and 20–40 minutes), not against plain dense retrieval. The paper's own rendered text also says 10–20x in one place. Its indexing is "around 10 times slower and $15 more expensive" per 10k passages ([HippoRAG](https://arxiv.org/html/2405.14831)). The quality gains are real for multi-hop questions: 2Wiki recall@5 is **90.4 vs 76.5** for dense retrieval in HippoRAG 2. But HippoRAG lost to ColBERTv2 on HotpotQA, and in the same paper GraphRAG trails dense retrieval on every dataset while LightRAG collapses to an average F1 of 6.6 ([HippoRAG 2](https://arxiv.org/html/2502.14802); [HippoRAG](https://arxiv.org/html/2405.14831)). An independent controlled comparison concludes that plain RAG wins on single-hop and detail questions, GraphRAG wins on multi-hop and reasoning, and adaptive hybrids gain consistently ([Han et al.](https://arxiv.org/abs/2502.11371)). GraphRAG's own evidence covers global sensemaking over ~1M-token corpora, with 72–83% comprehensiveness win rates ([GraphRAG](https://arxiv.org/html/2404.16130)), not local fact lookup. Its community summaries also need expensive rebuilds on update ([LightRAG](https://arxiv.org/html/2410.05779v3)), which is the wrong property for a brain that is written to continuously. The evaluation methods themselves disagree: LLM-judge win rates favor GraphRAG-style systems, while exact-match F1 does not. The practical conclusion is to use a HippoRAG-2-style passage–entity graph with Personalized PageRank as the *only* graph layer, and to route queries to it only when they are multi-hop.

## Cheap routers capture most of the adaptive-retrieval gain

Deciding *whether* and *how deeply* to retrieve saves more tokens than tuning the retriever. TARG drafts a short answer, gates retrieval on the logit margin of that draft, and reports **70–90% fewer retrievals than always-retrieve while matching or improving EM/F1** ([TARG](https://arxiv.org/abs/2511.09803)). Its signal needs token logprobs, which Anthropic's API does not expose, so a model-agnostic brain needs a substitute such as self-consistency or the retrieval score. Adaptive-RAG's three-way classifier (no retrieval, single-step, multi-step) matched multi-step F1 with GPT-3.5 (**50.91 vs 50.87**) at **1.46x vs 3.33x** the single-step time, even though the classifier was only **54.5% accurate**. An oracle router would have added another 6–12 F1 points *at lower cost* ([Adaptive-RAG](https://arxiv.org/html/2403.14403v2)). On RAGRouter-Bench, a plain **TF-IDF + SVM** router reached **93.2% accuracy and 28.1% simulated token savings**, beating embedding features ([RAGRouter-Bench](https://arxiv.org/abs/2604.03455)). A July 2026 evaluation found that "simple uncertainty or retrieval-score baselines often perform about as well as learned utility routers," that retrieval harm is non-negligible, and that calibrated thresholds miss their target usage rate on new data ([Qian et al.](https://arxiv.org/abs/2607.24010)). Self-Route's escalation pattern (try RAG, let the model say "unanswerable", then fall back to long context) kept within about 0–3 points of long context while using **38–61% of its tokens** ([Self-Route](https://arxiv.org/html/2407.16833v2)).

Model routing and caching layers add smaller, less certain gains. RouteLLM saved **3.66x** on MT Bench chat but only **1.4–1.5x** on MMLU and GSM8K, with router overhead of about $3 per million requests ([RouteLLM](https://arxiv.org/html/2406.18665)). FrugalGPT's "up to 98%" is a best case from 2023 datasets ([FrugalGPT](https://arxiv.org/abs/2305.05176)). Agentic plan caching cut cost **50.3%** and latency **27.3%** on repeated agent workflows ([APC](https://arxiv.org/abs/2506.14852)). That makes keyed plan and result caches attractive for recurring tasks. GPTCache-style fuzzy semantic caching of *answers* is risky for personal, time-dependent questions, and it is dangerous across tenants. KV-reuse systems are strong but apply only to self-hosted models: CacheBlend reports **2.2–3.3x lower TTFT** for non-prefix RAG chunks ([CacheBlend](https://arxiv.org/abs/2405.16444)), RAGCache up to **4x** lower TTFT ([RAGCache](https://arxiv.org/abs/2404.12457)), and SGLang up to **6.4x** throughput ([SGLang](https://arxiv.org/abs/2312.07104)). They matter if the service later hosts its own small extraction or answer models.

## Persistent memory turns one injection into a permanent compromise

A memory brain is a write-enabled store that ingests untrusted content and feeds it to agents that hold credentials. That is exactly Willison's "lethal trifecta" of private data, untrusted content and external communication ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). SpAIware showed an indirect injection from a web page writing an instruction into ChatGPT's long-term memory and exfiltrating all future chats ([The Hacker News](https://thehackernews.com/2024/09/chatgpt-macos-flaw-couldve-enabled-long.html)). MINJA showed that an attacker with *no* memory access can, through ordinary queries alone, plant records that are later retrieved for a different user's query. It reported **98.2% injection success and 76.8% attack success** across three agents ([MINJA](https://arxiv.org/html/2503.03704v2)), although a 2026 follow-up argues those conditions were idealized, with near-empty memories and fixed retrieval parameters ([arXiv 2601.05504](https://arxiv.org/html/2601.05504v1)). MCP adds its own risk: a malicious server's tool *description* silently redirected messages through a trusted WhatsApp server without ever being called ([Invariant Labs](https://invariantlabs.ai/blog/whatsapp-mcp-exploited)). For a multi-tenant service, MINJA's cross-user path is the decisive threat. Any shared index, shared semantic cache or shared "global learnings" store is a pipe for poisoning between tenants.

The mitigations that hold up are architectural. CaMeL separates a privileged planner from a quarantined parser of untrusted data and enforces data-flow capabilities ([CaMeL](https://arxiv.org/abs/2503.18813)). Meta's "Rule of Two" requires human approval when a session would combine untrusted input, sensitive data and state-changing actions ([Meta](https://ai.meta.com/blog/practical-ai-agent-security/)). Products add user-editable memory, incognito modes and scoped partitions: Claude isolates memory per Project, and Personal.ai partitions it per persona ([VentureBeat](https://venturebeat.com/ai/anthropic-adds-memory-to-claude-team-and-enterprise-incognito-for-all); [Personal.ai](https://docs.personal.ai/documentation/training/memory-stack)). Deletion is a weak spot. In ChatGPT, deleting a chat does not delete the saved memories derived from it ([OpenAI Help](https://help.openai.com/en/articles/8590148-memory-faq)), so derived facts need lineage pointers back to their source for a right-to-be-forgotten request to actually propagate. Over-personalization is the quieter risk. OpenAI rolled back a sycophantic GPT-4o update and attributed it partly to over-weighting short-term feedback ([OpenAI](https://openai.com/index/sycophancy-in-gpt-4o/)). A brain that stores user opinions as "facts" can amplify that effect, so style preferences and claims about the world belong in separately typed stores.

## The recommended brain: a cost-ordered cascade behind one MCP interface

The design below combines the evidence above into a model-agnostic service exposed as both an HTTP API and an MCP server. It has three core tools (`recall`, `remember`, `forget`), plus `profile` and `search_raw` for agentic escalation. Each component traces to a cited result. The latency and token figures are **engineering targets estimated from those results, not measurements**. Proving them is the point of the benchmark plan.

### Query-time pipeline

The service returns a compact *context packet*, not an answer. That keeps it model-agnostic and lets the client's own model, at whatever price tier, do the generation. The client places the packet after its cached prefix. The stages run in cost order, and each one can end the pipeline.

| Stage | What it does | Evidence | Target brain-side latency | Uncached tokens added |
|---|---|---|---|---|
| 0. Keyed result/plan cache | Exact-key lookup on (tenant, ACL scope, normalized intent, memory version). Any write to the relevant facts invalidates the entry. No fuzzy matching across tenants | [APC](https://arxiv.org/abs/2506.14852) | 1–3 ms | 0 on hit |
| 1. Pinned profile block | ≤1,000-token tenant/user profile (preferences, active projects, key entities), rebuilt in batches. The client caches it with a 1-hour TTL | [Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [PrefEval](https://arxiv.org/abs/2502.09597v1) | 0 (in prefix) | ~0; billed at 0.025–0.1x |
| 2. Router | Rules (private entity, time words) plus a TF-IDF/SVM classifier choosing: none / fact lookup / multi-hop / global / raw search. Time-aware query expansion | [RAGRouter-Bench](https://arxiv.org/abs/2604.03455); [Qian et al.](https://arxiv.org/abs/2607.24010); [LongMemEval](https://arxiv.org/abs/2410.10813) | <1 ms | 0 |
| 3. Fact lookup (default path) | BM25 + int8 dense over *currently valid* facts in the tenant namespace, fused with RRF, top 5–15. Exact flat search below ~1M items, HNSW/DiskANN above | [Zep](https://arxiv.org/html/2501.13956); [HF quantization](https://huggingface.co/blog/embedding-quantization); [DiskANN](https://proceedings.neurips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html) | 5–30 ms | 300–800 |
| 4. Conditional rerank | Small cross-encoder over the top 20–50, only when fused scores are close | [Zep](https://arxiv.org/html/2501.13956) | +50–200 ms (GPU) | 0 (reorders) |
| 5. Multi-hop graph | Seed entities → Personalized PageRank on the passage–entity graph (HippoRAG 2 style) | [HippoRAG 2](https://arxiv.org/html/2502.14802) | 100–500 ms | 500–1,500 |
| 6. Escalation | When the model answers "unanswerable": agentic `search_raw` over episodes (Letta style), or a bounded long-context slice cached for follow-ups | [Self-Route](https://arxiv.org/html/2407.16833v2); [Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory) | 1–3 s (rare) | 2k–10k |
| 7. Packing | Facts rendered as one-line records with valid-from dates, status, source ID and trust tier. Optional LLMLingua-2 at ≤2x on raw-episode prose only. The packet may be empty | [MERIT](https://arxiv.org/abs/2609.05441); [LLMLingua-2](https://arxiv.org/abs/2403.12968); [RECOMP](https://arxiv.org/abs/2310.04408) | 1–20 ms | –30–50% on prose |

Under these targets, a typical query spends **~20–60 ms at p50 and under ~250 ms at p95** in the brain on the default path. For comparison, Mem0's measured search time was 0.148 s p50 / 0.200 s p95, and Zep's corrected p95 was 0.632 s ([Mem0](https://arxiv.org/html/2504.19413); [Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). The token target is **~600–1,200 uncached context tokens** on the default path, plus a ~1,000-token cached profile that bills at 0.025–0.1x. That works out to an effective **~700–1,300 full-price-equivalent tokens**, against 1,764 for Mem0, 1.6k–3.9k for Zep, and 26k–115k for full context. Queries routed to "none" or answered from cache cost close to nothing. If the router behaves the way TARG's and Adaptive-RAG's results suggest, a large share of turns never reach Stage 3 at all. End-to-end latency will still be dominated by the client's LLM: Mem0's *total* p50 with gpt-4o-mini was 0.71 s against 0.148 s of search ([Mem0](https://arxiv.org/html/2504.19413)). The brain's real lever on wall-clock time is the shorter prompt. Fewer input tokens and a warm cache both cut time-to-first-token.

### Write and consolidation pipeline

Writes run off the critical path, the way Mem0 refreshes its summary asynchronously ([Mem0](https://arxiv.org/html/2504.19413)), so a stored memory adds no query latency. To keep reads consistent with recent writes, the client keeps the last few raw turns in context until extraction finishes. The write pipeline has six steps.

**1. Append the episode.** Every message, document or tool result goes to an immutable, timestamped, tenant-partitioned and encrypted episodic log. This is the non-lossy ground truth, as in Zep's episode tier ([Zep](https://arxiv.org/html/2501.13956)). Each episode is tagged with a provenance class: user-stated, assistant-stated, inferred, or ingested from external content.

**2. Extract facts.** A small, cheap model extracts atomic facts and entities from *both* speakers, to avoid Zep's single-session-assistant loss. Facts are stored at round or fact granularity, with fact-augmented index keys ([LongMemEval](https://arxiv.org/abs/2410.10813)). Batching extraction per session-chunk instead of per turn amortizes its cost.

**3. Reconcile.** Each candidate fact is compared against its top-10 most similar existing facts, and one operation is chosen: ADD, UPDATE, INVALIDATE or NOOP. This is Mem0's operation set, with DELETE replaced by Zep-style bi-temporal invalidation that keeps both the valid-time and ingest-time clocks ([Mem0](https://arxiv.org/html/2504.19413); [Zep](https://arxiv.org/html/2501.13956)).

**4. Enforce trust tiers.** Content in the "ingested from external content" class can create episodes and *candidate* facts. It cannot overwrite user-stated facts or the profile without confirmation. This applies Rule-of-Two logic to the memory-write sink, which is the direct countermeasure to SpAIware and MINJA ([Meta](https://ai.meta.com/blog/practical-ai-agent-security/); [MINJA](https://arxiv.org/html/2503.03704v2)).

**5. Index.** New facts get BM25 entries, int8 or Matryoshka embeddings, and OpenIE triples linked into a passage–entity graph. HippoRAG 2's indexing costs about **8x fewer tokens than LightRAG and ~12x fewer than GraphRAG** ([HippoRAG 2](https://arxiv.org/html/2502.14802)). GraphRAG-style community summaries are skipped because they need expensive rebuilds on update ([LightRAG](https://arxiv.org/html/2410.05779v3)).

**6. Consolidate during idle time ("sleep").** On a schedule, the system rebuilds the pinned profile in one batch, so the cached prefix changes rarely. It writes reflections and summaries that link to their evidence and can be regenerated. It decays the ranking weight of stale, never-recalled items, and it propagates deletions through lineage pointers so derived facts disappear with their source.

For company use, every query, cache key and index lookup carries the tenant ID and the caller's ACL scope as a hard pre-filter, applied before retrieval rather than as a post-filter. Large enterprise tenants get their own approximate-search shards. Small tenants share infrastructure but never share index namespaces, semantic caches or consolidated "learnings." For personal agents, the same service runs single-tenant, or local, where exact flat search makes the vector layer trivial.

## A benchmark plan that would survive the Mem0–Zep dispute

The comparison must be one public harness, run with multiple seeds, in which every baseline is configured the way its own vendor recommends. That last condition addresses both of Zep's complaints (role mapping, `created_at`, concurrent searches) and Mem0's (shared prompt template, ≥10 runs) ([zep-papers#5](https://github.com/getzep/zep-papers/issues/5)). The baselines are full context, Mem0, Mem0g, Zep/Graphiti, the Letta filesystem agent, HippoRAG 2 and plain hybrid RAG. Every system uses the same answer models (one cheap and one frontier, from two different providers to demonstrate model-agnosticism) and the same judge. Vendors get a pre-registration window to review their configurations before the runs.

The dataset suite should cover each known weakness. **LongMemEval_S and _M** are the primary accuracy test because they include knowledge updates and abstention ([LongMemEval](https://arxiv.org/abs/2410.10813)). **LoCoMo categories 1–4** are included only for backward comparability, with its flaws disclosed. **MERIT** measures updated-fact correctness, the act-on-retrieved-value rate and dollars ([MERIT](https://arxiv.org/abs/2609.05441)). **PrefEval** tests preference retention ([PrefEval](https://arxiv.org/abs/2502.09597v1)). **MuSiQue and 2Wiki** compare multi-hop performance against HippoRAG on its home turf ([HippoRAG 2](https://arxiv.org/html/2502.14802)). A **MINJA-style poisoning suite**, run at realistic memory sizes as the 2026 critique demands ([arXiv 2601.05504](https://arxiv.org/html/2601.05504v1)), measures attack success, plus a cross-tenant leakage test that should score zero. A synthetic multi-year, multi-source corpus covers a gap no public benchmark fills.

Each system reports the same metrics. Accuracy is broken down by category, with confidence intervals over ≥5 seeds. Latency is split into search and total time, at p50, p95 and p99, with concurrency held fixed. Uncached input tokens, cached tokens and output tokens are reported separately, because compression-induced output growth must be caught ([arXiv 2603.23527](https://arxiv.org/abs/2603.23527)). Write-side cost is reported in tokens and dollars per 1,000 ingested turns, along with store footprint, freshness lag (time from a write until it is retrievable), and the router's realized retrieval rate and harm rate ([Qian et al.](https://arxiv.org/abs/2607.24010)). The success criterion is **non-inferiority on accuracy** (a lower confidence bound no worse than −1 point against the best baseline on LongMemEval and MERIT), together with **≥2x fewer billed full-price-equivalent tokens and ≥2x lower p95 search latency** than the strongest accuracy baseline. Ablations remove one stage at a time (router, invalidation, graph, rerank, cache layout, trust tiers) so that each claimed saving can be attributed to a component. The harness, configurations and raw outputs are published.

## Open problems the architecture cannot yet solve

Several gaps remain open in the literature, and this design inherits them. Routing quality is the bottleneck. Adaptive-RAG's oracle gap is 6–12 F1 points ([Adaptive-RAG](https://arxiv.org/html/2403.14403v2)), thresholds drift across datasets ([Qian et al.](https://arxiv.org/abs/2607.24010)), and no published router accounts for *whether a long-context prefix is already warm in the provider cache*. Under 2026 cache prices, that could make stuffing a stable document cheaper than retrieving from it. Logprob-free uncertainty gating for closed APIs has not been validated against TARG-style gates. LLM-extracted graphs inject noise, and nobody has a cheap way to verify or repair the triples ([HippoRAG 2](https://arxiv.org/html/2502.14802)). The retrieve-versus-act gap (55% in MERIT) suggests the next gains will come from learned memory *policies*, which the 2026 survey describes as "becoming a trainable capability" ([Huang et al.](https://arxiv.org/abs/2602.06052)), rather than from better indexes. Provable deletion from derived summaries, standard memory interchange formats, the value of explicit Ebbinghaus-style forgetting compared with supersession alone, and benchmarks built on multi-year real personal corpora all lack primary evidence. Compression of code and of multi-turn agent trajectories is barely studied ([Cmprsr](https://arxiv.org/html/2511.12281)). Finally, provider cache pricing changed materially in 2026, and any cost model, including the one in this report, goes stale within months.

## Conclusion

The literature has shifted the optimization target. In 2023 the question was how to shrink the prompt or how to structure the store, whether as a vector index, a graph or a tree. By late 2026 the evidence says storage structure matters less than three decisions: **when to consolidate** (at write time, with invalidation rather than deletion), **whether to retrieve at all** (cheap routers, an allowed empty result, escalation on "unanswerable"), and **what never changes between calls** (a stable, cached prefix). Speed and token cost both follow from those decisions, because the fastest token is one that is never sent and the second fastest is one billed at a tenth of the price. A brain service that wins on these terms can let the client choose any model, which is the practical meaning of "model-agnostic."

The strategic opening is credibility, not cleverness. Mem0, Zep and Letta each publish numbers that the others dispute, and no neutral harness exists. A service that ships the cascade above *and* the open, vendor-reviewed benchmark harness, with token, dollar, latency, poisoning and cross-tenant leakage metrics reported side by side, would define the evaluation standard that the current leaders have failed to agree on. If the non-inferiority test fails on LongMemEval updates or MERIT's act rate, that result would itself be valuable: it would show that the remaining gap lies in memory policy, which is where the next generation of trainable brains will compete.
